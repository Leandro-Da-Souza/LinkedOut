# LinkedIn integration boundaries

Milestone one does not connect to LinkedIn, request OAuth, scrape content, publish posts, send messages, or claim LinkedIn outcomes. Its provenance identifies user-provided briefs and profile configuration. Future integrations must establish both endpoint access and permission for the intended use; human approval does not authorize a prohibited integration.

The following capability assessment was researched for the architecture on October 13, 2026. Recheck official documentation and applicable agreements before implementing each capability; API products, scopes, and access requirements can change.

## Policy constraints

LinkedIn's base API Terms prohibit using its content or APIs to automate posting. Additional program agreements can control conflicting provisions. Reviewed, immediate, user-initiated sharing appears consistent with the Share product, but that interpretation needs confirmation for the specific integration. Scheduled publishing stays disabled until applicable permission and agreements establish authorization. [API Terms](https://www.linkedin.com/legal/l/api-terms-of-use)

The Developer AI Policy distinguishes permitted uses of Marketing API data. Consented application users' own content can support content creation and editing. Other people's API-retrieved content has narrower allowed uses such as prioritization and categorization; it cannot be assumed permissible input for generated replies. Independently supplied information has different treatment, but imports need provenance and valid rights. [Developer AI Policy](https://learn.microsoft.com/en-us/linkedin/marketing/developer-ai-policy)

Community Management member data cannot be repurposed for sales prospecting, recruiting, CRM enrichment, mass messaging, or reproducing a feed. Therefore a networking feature cannot treat Community Management as a general prospect database. [Restricted uses](https://learn.microsoft.com/en-us/linkedin/marketing/restricted-use-cases)

Scraping, unofficial APIs, prohibited browser automation, and scraped dataset imports are excluded. Manual input is a fallback for authorized information, not a way to bypass source restrictions. [Automation and scraping policy](https://www.linkedin.com/help/linkedin/answer/a1341387/prohibition-of-scraping-software)

## Required future integration controls

- Report capability availability with concrete reasons: available, missing scope, missing product approval, disallowed use, or manual-only. Never fabricate activity or successful actions.
- Preserve origin, permitted uses, consent where needed, retention/deletion deadlines, and downstream derivations. Enforce these rules before model input or export, including through MCP. Restricted content must not survive deletion in logs, summaries, embeddings, or memory. [Storage requirements](https://learn.microsoft.com/en-us/linkedin/marketing/data-storage-requirements)
- Obtain minimal OAuth scopes and validate state/redirects. Store tokens securely; refresh access is not universal. [Authentication](https://learn.microsoft.com/en-us/linkedin/shared/authentication/getting-access), [Refresh tokens](https://learn.microsoft.com/en-us/linkedin/shared/authentication/programmatic-refresh-tokens)
- Bind trusted human approval to the exact account, target, payload, revision, and expiry. Invalidate it when the content changes. Models cannot approve their own actions.
- Persist external action intent and audit history, apply idempotency, and require authoritative provider evidence of success. Resolve ambiguous sends before any retry. Expose supported application operations rather than a raw API proxy.

Until these controls and access requirements are satisfied, LinkedOut can research independently authorized sources, create drafts, organize a calendar, recommend manual interactions, and track user-confirmed outcomes.
